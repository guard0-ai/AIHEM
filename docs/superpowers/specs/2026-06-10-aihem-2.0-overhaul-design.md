# AIHEM 2.0 — AI / Agent / MCP Security Governance & Accountability Range (Master Design)

**Date:** 2026-06-10
**Status:** Approved (master design); sub-project specs to follow
**Author:** brainstorming session
**Supersedes:** AIHEM v1.0.0 (2024) challenge model

---

## 1. Vision

Transform AIHEM from a 2024-era "prompt-injection + SQLi" lab into the **most exhaustive
AI / agent / MCP security governance and accountability range** of June 2026 — and, on the
same neutral core, the **best possible live demo for Guard0.ai**.

The reframe is the headline: AIHEM stops being a pure *exploitation* playground and becomes
a **full-lifecycle range**. For each scenario a learner can:

1. **Break** it — perform the exploit (classic CTF).
2. **Observe** it — inspect a tamper-evident accountability trail and find the forensic
   evidence of their own attack (detection / attribution).
3. **Govern** it — author or enable a policy that should block it.
4. **Verify** it — re-run the exploit and confirm the policy blocked it *and* that the audit
   trail proves the denial.

No existing app (OWASP PromptMe, LLMGoat, Damn Vulnerable MCP Server, ReversingLabs
Vulnerable MCP Servers Lab) offers this break→observe→govern→verify loop or unifies all
three current OWASP AI frameworks in one runnable agent-native system. That integration is
the differentiator and the basis for an OWASP contribution claim.

### Why now (June 2026)

The current platform is ~2 years stale (2023 OWASP LLM Top 10, no MCP, stub "agent"). The
surfaces that define 2025–2026 AI security are absent:

- The **2025 OWASP LLM Top 10** revision.
- The **OWASP MCP Top 10** — tool poisoning, rug-pull updates, confused-deputy, injection
  via tool descriptions/responses, token/credential theft, malicious servers, cross-server
  shadowing.
- The **OWASP Top 10 for Agentic Applications 2026 (ASI01–ASI10)** — goal hijack, tool
  misuse, identity/privilege abuse, agentic supply chain, unexpected code execution,
  memory/context poisoning, insecure inter-agent comms, cascading failures, human-agent
  trust exploitation, rogue agents.
- **Governance & accountability** for agents — policy enforcement at the tool/MCP boundary,
  tamper-evident audit, and cross-agent attribution — which almost no public lab exercises.

### Competitive positioning (verified June 2026)

| Project | Covers | Gap AIHEM 2.0 fills |
|---|---|---|
| OWASP PromptMe | LLM Top 10 (LLM-app centric) | No MCP, no agentic, no governance loop |
| LLMGoat | LLM Top 10 (WebGoat-style) | Same |
| Damn Vulnerable MCP Server / RL Lab | MCP server attacks (narrow) | No agent/LLM range, no governance/accountability |

"Most exhaustive" is claimed on **integration + tri-framework completeness + the
governance/accountability loop**, not raw challenge count.

## 2. Approach decision

Agent authenticity — three options considered:

- **A — Simulated/scripted agent:** cheapest, but a fake agent undercuts the point in 2026.
- **B — Real agent loop with a swappable brain (CHOSEN):** one orchestrator with a real
  ReAct/tool-calling loop, a deterministic `MockBrain` for offline/CTF reliability, and an
  `LLMBrain` for BYO-key realism. Grading keys off observable side-effects → deterministic
  regardless of brain.
- **C — Always-real LLM:** most authentic but non-deterministic and needs keys (ruled out).

**Locked decisions:**

| Decision | Choice |
|---|---|
| Scope | Full platform + content overhaul |
| Taxonomy anchors | OWASP LLM Top 10 (2025) + OWASP MCP Top 10 + OWASP Agentic Top 10 (2026, ASI01–ASI10) + MITRE ATLAS (cross-ref) |
| LLM backbone | Deterministic core + optional real LLM (BYO key / local) |
| Tech foundation | Evolve current stack: Python/FastAPI microservices + Docker Compose + React |
| Agent authenticity | Approach B — real loop, swappable `MockBrain`/`LLMBrain` |
| Governance/accountability | First-class planes via neutral interfaces + reference implementation |
| Dual positioning | Vendor-neutral OWASP core; Guard0 as one optional adapter, isolated in `integrations/guard0/` |

## 3. Architecture — one core, three planes, one optional overlay

Evolve the current FastAPI + Docker Compose + React stack.

```
              ┌──────────── Guard0 adapter (OPTIONAL, separate, Compose profile) ─────────┐
              │   reference control layer plugged into the SAME neutral PDP + telemetry    │
              └───────────────────────────────▲──────────────────────────────────────────┘
                                               │ neutral interfaces
 ┌──────────────┐  action  ┌──────────────────┴────────┐  event  ┌────────────────────────┐
 │  AGENT CORE  │────────► │ GOVERNANCE PLANE           │ ──────► │ ACCOUNTABILITY PLANE   │
 │ orchestrator │ ◄─────── │ policy-gateway (PDP) +     │         │ hash-chained audit log │
 │ +MCP host    │allow/deny│ reference rules engine     │         │ + attribution graph    │
 │ +memory      │/transform│ (OFF by default)           │         │ (tamper-evident)       │
 │ +sub-agents  │/approve  └────────────────────────────┘         └────────────────────────┘
 └──────────────┘
        ▲ LLM / MCP / agentic attack surface (the exploit targets)
```

### Services

| Service | Status | Role |
|---|---|---|
| **agent-orchestrator** | NEW (replaces stub `agent-service`) | Real ReAct loop; pluggable `MockBrain`/`LLMBrain`; tool registry; planner; sub-agent delegation; **MCP host**. Emits events to audit bus; consults PDP before every action. |
| **agent-memory** | NEW | Persistent, *poisonable* memory store (Redis/pg-backed). No provenance checks by default. |
| **mcp-servers** (×3–4) | NEW | Real but vulnerable MCP servers: `files-mcp`, `tickets-mcp`, `notes/email-mcp`, `third-party-mcp` (malicious "marketplace" server). |
| **policy-gateway (PDP)** | NEW | Governance plane. Neutral interface `evaluate(action, context) -> {allow|deny|transform|require_approval}`. Ships a reference YAML/Rego-style rules engine. **Disabled by default** so the range is vulnerable; learners enable it in the Govern phase. |
| **audit-service** | NEW | Accountability plane. Append-only, hash-chained (tamper-evident) event log: actor identity, agent/sub-agent id, tool, MCP server, redacted args, policy decision, outcome. Serves a queryable trail + **attribution graph**. |
| **exfil-collector** | NEW | Sink that records when secrets/tokens leave the system (deterministic grading). |
| rag-service | REFRESH | Vector/embedding weaknesses (LLM08-2025). |
| model-registry | REFRESH | Supply chain / model provenance (LLM03-2025, ASI04). |
| chatbot-service | REFRESH | Prompt injection / system-prompt leakage (LLM01/LLM07-2025). |
| auth-service | KEEP | Identity for confused-deputy, token-theft, ASI03 scenarios. |
| challenge-validator | UPGRADE | Multi-phase, side-effect deterministic grading (see §5). |
| **guard0-adapter** | NEW, OPTIONAL | Reference control-layer adapter implementing the PDP interface + consuming the telemetry bus. Lives in `integrations/guard0/`, behind a Compose profile; splittable to a separate repo for the OWASP submission. **Not part of the neutral OWASP artifact.** |

### Neutral interface contracts (the key to dual positioning)

- **PDP interface:** `evaluate(action, context) -> decision`. The reference engine and the
  Guard0 adapter are interchangeable implementations. Selected by config/env.
- **Telemetry bus:** structured events (`actor`, `agent_id`, `parent_agent_id`, `tool`,
  `mcp_server`, `args_redacted`, `decision`, `outcome`, `hash`, `prev_hash`). Consumed by
  audit-service and (optionally) Guard0.
- **brain interface:** `decide(state) -> action`. `MockBrain` (deterministic, obeys injected
  instructions by design) and `LLMBrain` (provider adapter).
- **agent-memory:** `read(session)`, `write(session, entry)`, `search(query)` — poisonable.
- **mcp-server:** standard MCP tool listing + invocation; each ships an intentional flaw.

Because Guard0 plugs into the *same* interfaces the reference engine uses, the Guard0 demo
is a real product on a standard range — not a rigged demo — while the OWASP core stays
vendor-neutral.

## 4. Challenge catalog (the 2026 content)

~50 challenges. The new MCP, agentic, and governance/accountability tracks are the headline.

1. **Prompt Injection & System Prompt** (refresh) — LLM01 / LLM07-2025
2. **MCP Exploitation** (NEW) — tool poisoning, rug-pull updates, confused-deputy, injection
   via tool descriptions/responses, OAuth/token theft via malicious server, cross-server
   tool shadowing → OWASP MCP Top 10
3. **Agentic Exploitation** (NEW) — mapped to exact ASI codes:
   - ASI01 Agent Goal Hijack
   - ASI02 Tool Misuse & Exploitation
   - ASI03 Agent Identity & Privilege Abuse
   - ASI04 Agentic Supply Chain Compromise
   - ASI05 Unexpected Code Execution
   - ASI06 Memory & Context Poisoning
   - ASI07 Insecure Inter-Agent Communication
   - ASI08 Cascading Agent Failures
   - ASI09 Human-Agent Trust Exploitation
   - ASI10 Rogue Agents
4. **Governance & Accountability** (NEW) — challenges that attack the control planes
   themselves: policy bypass, audit-log evasion / tampering (defeating the hash chain),
   broken cross-agent attribution, approval-workflow bypass, redaction bypass.
5. **RAG / Vector & Embedding** (refresh) — LLM08-2025
6. **Supply Chain & Model Provenance** (refresh) — LLM03-2025
7. **Improper Output Handling & Downstream** (refresh) — LLM05-2025
8. **Sensitive Info Disclosure** (refresh) — LLM02-2025
9. **Unbounded Consumption** (replaces old Model DoS) — LLM10-2025

Each challenge entry in `challenges.yaml` carries: `owasp_llm_2025`, `owasp_mcp`,
`owasp_asi_2026`, `mitre_atlas`, `governance_dimension`, and the `phases` it supports
(Break / Observe / Govern / Verify).

## 5. Grading & the Break → Observe → Govern → Verify loop

Challenges declare up to four graded phases; easy ones may be Break-only, headline
agentic/MCP ones get all four:

1. **Break** — exploit succeeds (observable side-effect: secret hit exfil-collector, tool
   fired, memory contains payload).
2. **Observe** — learner queries the audit trail / attribution graph and identifies the
   evidence (graded by submitting the correct event id / attribution path).
3. **Govern** — learner enables/authors a policy in the policy-gateway.
4. **Verify** — exploit is replayed; validator confirms (a) side-effect did NOT occur and
   (b) audit log shows a `deny`/`transform` decision attributable to the new policy.

All grading is **deterministic side-effect based**, so `MockBrain` and `LLMBrain` both
produce repeatable outcomes. Text flags (e.g. `AIH3M_...`) remain for pure text-extraction
challenges.

## 6. Exhaustiveness bar — 3-axis coverage matrix

A generated coverage-matrix document + CI check enforces completeness. Every cell must have
≥1 challenge:

- **OWASP LLM Top 10 (2025):** LLM01–LLM10
- **OWASP MCP Top 10:** all categories
- **OWASP Agentic Top 10 (2026):** ASI01–ASI10
- **MITRE ATLAS:** cross-reference (not a completeness axis, but every challenge is tagged)

"Exhaustive" is defined as a full matrix, not a challenge count. CI fails if any cell is
empty.

## 7. Decomposition & build order

Full overhaul, decomposed into sub-projects; each gets its own spec → plan → build:

1. **Agentic core + deterministic brain** — foundation; everything depends on it.
2. **Accountability plane** — telemetry bus, hash-chained audit log, attribution graph.
3. **Governance plane** — policy-gateway (PDP) + reference rules engine + neutral interface.
4. **MCP attack surface** — vulnerable MCP servers + host integration.
5. **Agentic + governance challenge tracks** — ASI01–ASI10 + control-plane attacks, with the
   4-phase loop.
6. **Taxonomy refresh + coverage matrix** — re-map existing services/challenges to 2025
   OWASP; generate + CI-enforce the matrix.
7. **Validator / scoring v2** — multi-phase, side-effect grading + exfil sink.
8. **Frontend + docs refresh** — new-track UI, governance dashboard, attribution-graph
   visualization, coverage matrix, walkthroughs, researcher guide, bump to v2.0.
9. **Guard0 integration overlay** (separate) — Guard0 adapter on the neutral interfaces;
   demo scripts; splittable to its own repo.

**Order rationale:** core (1) first; accountability (2) and governance (3) planes next since
all challenge phases depend on them; MCP (4) and tracks (5) plug in; taxonomy/matrix (6) and
validator (7) make it gradable and exhaustive; frontend/docs (8) last; Guard0 (9) is an
independent overlay buildable any time after (2)+(3).

**Next step:** brainstorm **sub-project 1 (agentic core)** in full detail.

## 8. Dual-positioning & OWASP contribution

- **OWASP artifact** = core + accountability + governance planes + reference policy engine +
  challenge catalog + coverage matrix. **Zero Guard0** branding or coupling. Apache-2.0
  (already in place). Intake path: Incubator → Lab → Flagship; acceptance hinges on filling a
  real gap (the tri-framework agentic + governance integration) rather than duplicating
  PromptMe/LLMGoat.
- **Guard0 demo** = same range with the Guard0 adapter enabled. Because Guard0 implements the
  same neutral PDP + telemetry interfaces as the reference engine, the demo shows a real
  control layer governing a standard OWASP range and producing the accountability story —
  credible, not rigged.
- **Vendor-neutrality guardrail:** nothing in the OWASP-submitted tree may reference Guard0;
  the adapter and demo assets live only under `integrations/guard0/` (or a separate repo).

## 9. Non-goals / YAGNI

- No production hardening — intentionally vulnerable, isolated-only.
- No bundled local model in core (BYO key or user-supplied local endpoint only).
- No rewrite to a non-Python stack.
- No Guard0 coupling in the neutral core.
- No unrelated refactoring beyond what each track requires.
- Existing safety warnings, license, and isolation guidance are preserved.
